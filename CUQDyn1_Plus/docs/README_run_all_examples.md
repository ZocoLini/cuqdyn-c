# README: `run_all_examples.m`

## Purpose

`run_all_examples.m` is the master smoke/integration runner for the maintained
non-SBC CUQDyn1_Plus examples. It is intended to answer one practical question:

> Do the standard examples still execute successfully and produce plausible
> CUQDyn result files after code or documentation changes?

The runner is not a benchmarking script and is not meant to replace the
dedicated SBC calibration scripts. SBC scripts are intentionally excluded
because they are much more expensive and answer a different statistical
calibration question.

## What It Runs

The manifest inside `run_all_examples.m` currently includes the maintained
examples for:

- LV
- SIR
- AP
- NFKB
- LinearCascade
- LinearCascade3

The labels intentionally match the example/model folder names used elsewhere
in the repository. The LinearCascade entries run known-truth diagnostic scripts,
but the summary `Name` column still uses the model name.

For examples that support both methods, the runner executes both
`CUQDyn1_Plus` and `CUQDyn1_Plus_HybridCov` variants.

Each example is run from its own example folder, while the repository root is
added to the MATLAB path. The runner executes each script in the base workspace
so legacy example scripts that use `clear all` do not erase the runner itself.

## How To Run

From the repository root in MATLAB:

```matlab
summary = run_all_examples();
```

To stop at the first failure:

```matlab
summary = run_all_examples('StopOnFailure', true);
```

The full suite can take a long time because each example may run global
optimization, ODE solves, LOO refits, figure generation, and Excel export.

## Output Folder

Every run creates a timestamped folder under `EXAMPLES`, for example:

```text
EXAMPLES/Master_Run_Results_YYYY-MM-DD_HH-mm-ss/
```

That folder contains:

- `master_example_run_summary.xlsx`
- `master_example_run_summary.csv`
- `master_example_run_summary.mat`
- one text log per example script

The per-example logs contain the captured MATLAB Command Window output from
each example. The summary files contain one row per example/method run.

## Summary Columns

The most important summary columns are:

- `Name`: example name.
- `Method`: CUQDyn method variant.
- `Status`: final runner status.
- `ElapsedSeconds`: wall-clock runtime for that example.
- `NErrors`: number of structural or validation errors detected.
- `NWarnings`: total warning count.
- `NExpectedWarnings`: warnings classified as expected.
- `NUnexpectedWarnings`: warnings classified as unexpected.
- `Script`: full path to the script that was run.
- `ResultDir`: result folder reported by the example.
- `LogFile`: captured Command Window log for that example.
- `Errors`: detailed error messages, if any.
- `Warnings`: human-readable warning messages.
- `WarningIDs`: stable warning identifiers.
- `WarningSources`: script path associated with each warning.
- `WarningClasses`: `expected` or `unexpected`.
- `WarningDetails`: combined warning class, ID, source, and message.

## Status Values

`PASS` means the script executed, produced the expected result folder and result
MAT file, and passed basic sanity checks without warnings.

`PASS_WITH_WARNINGS` means the script executed and produced structurally valid
outputs, but one or more warnings were recorded. Inspect `NUnexpectedWarnings`,
`WarningIDs`, and `WarningDetails` to decide whether action is needed.

`UNEXPECTED` means the script ran but the output failed a structural or numeric
sanity check. Examples include missing result files, missing required result
fields, non-finite numeric arrays, invalid UQ interval widths, or tolerance
failures in known-truth diagnostic summaries.

`ERROR` means the script itself threw an exception.

If any row has `ERROR` or `UNEXPECTED`, `run_all_examples.m` raises an error at
the end after writing all summary files. This behavior is intentional: automated
or manual callers get a clear failure signal, while the saved summary files
remain available for diagnosis.

## Warning Capture

The runner records two broad sources of warnings:

1. Runtime warnings emitted while the example script runs.
2. Post-run sanity-check warnings generated by `run_all_examples.m`.

Warnings are stored with stable IDs where possible. New or unrecognized warning
IDs are classified as `unexpected` by default so they stand out in the summary.
Known benign numerical warnings can be classified as `expected` inside
`run_all_examples.m`.

This warning capture adds negligible overhead compared with the optimizer, ODE,
LOO, plotting, and Excel-writing work performed by the examples. It affects only
the master runner; running an individual example script directly does not use
this extra summary layer.

## Interpreting The Results

A clean run has all rows marked `PASS` or, where understood and acceptable,
`PASS_WITH_WARNINGS` with `NUnexpectedWarnings = 0`.

If `NUnexpectedWarnings > 0`, inspect:

- `WarningIDs`
- `WarningSources`
- `WarningDetails`
- the corresponding per-example log file

Unexpected warnings do not necessarily mean the example failed, but they are a
signal that behavior changed or that a warning has not yet been classified.

If `NErrors > 0` or `Status` is `UNEXPECTED`, inspect the `Errors` column first.
These rows usually indicate missing outputs, invalid result structs, failed
numeric sanity checks, or known-truth diagnostic tolerances that were exceeded.

If `Status` is `ERROR`, inspect both the `Errors` column and the corresponding
per-example log.

## Scope And Limitations

`run_all_examples.m` is a broad integration check. It confirms that maintained
examples still run and produce structurally plausible outputs, but it does not
provide statistical coverage guarantees. For coverage and calibration claims,
use the dedicated SBC scripts in the example folders.

The runner also does not commit, delete, or curate generated result folders.
Generated outputs should remain outside Git unless explicitly needed for a
release artifact or report.
